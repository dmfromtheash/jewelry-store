# AURELIA — Возможности и ограничения (Features & Limits v1)

> **Назначение.** Честный список того, что AURELIA умеет **сегодня**, что работает
> в **ручном (MVP) режиме**, что относится к **будущему / зависит от провайдера**, и
> чего **пока нет**. Документ нужен, чтобы покупатель оценивал продукт без иллюзий.
>
> **Принцип:** лучше недо-обещать. Никаких заявлений о реальных платёжных/почтовых
> API, уведомлениях, продакшн-хостинге или юридическом соответствии, которых нет.

Рынок: **Украина**. Валюта витрины: **₴ (UAH)**. Модель оплаты/доставки v1:
**ручная**. Стек: Next.js 15 / React 19 / Prisma / PostgreSQL.

---

## 1. ✅ Готово сейчас (реальный рабочий код, БД PostgreSQL)

**Каталог и витрина**
- Каталог в **PostgreSQL** (категории, товары, варианты, изображения).
- Витрина: главная, категории (`bijouterie`, `gifts`), страницы товара
  (`/product/[slug]`), информационные страницы.
- Отображение цен в **₴ (UAH)**.

**Товары**
- Создание / редактирование товара в админке (поля, цена, статус).
- **Публикация / скрытие** товара: скрытый товар не виден на витрине и его
  **нельзя заказать**.
- **Главное изображение + галерея** товара (управление в админке).
- **Варианты товара** (например, покрытие): управление в админке + реальный
  **селектор варианта на витрине**; вариант по умолчанию; надбавка к цене
  (priceDelta); SKU варианта.
- **Остатки на складе**: на уровне товара и фундамент остатков на уровне
  вариантов.

**Корзина и оформление**
- Клиентская корзина (localStorage); идентичность строки — **`slug + variantId`**
  (один товар в двух вариантах = две строки).
- Безопасная подстановка для **старых** строк корзины без `variantId` (падают в
  вариант по умолчанию).
- Защиты корзины/чекаута: скрытые / недоступные / распроданные позиции **не ломают**
  корзину и **блокируются** при оформлении.
- **Гостевое оформление** (без регистрации).
- Ручные опции **доставки**: Самовывоз / Новая Почта / Укрпочта / Курьер +
  свободное поле (отделение/адрес/комментарий).
- Ручные опции **оплаты**: «Оплата при получении» / «Онлайн-оплата по реквизитам».
- **Инлайн-подтверждение** заказа с номером (`AUR-XXXXXXXX`); очистка корзины.
- **Серверно-авторитетная** цена: клиент присылает только slug + qty + вариант,
  а цену/имя/статус/вариант пересчитывает сервер (подделать цену с клиента нельзя);
  деньги хранятся в целых **минор-единицах**.

**Админка / заказы**
- Локально-защищённый вход в админку, журнал действий (audit log), `noindex` на
  админ-маршрутах.
- **Входящие заказы** (список) и **детальная карточка** со снимком позиций,
  выбранного варианта, способов оплаты/доставки, контактов и итога.
- **Жизненный цикл заказа**: `submitted → processing → completed / cancelled`
  с контролем допустимых переходов (терминальные статусы не воскрешаются).
- **Возврат остатка при отмене** заказа (для учитываемых товаров/вариантов).

**Аккаунты покупателей (Этапы 47A–47C)**
- **Регистрация / вход / выход** покупателя; пароли хэшируются (**scrypt**, соль,
  постоянное время сравнения) — пароль **никогда** не хранится и не логируется в
  открытом виде.
- **Отдельная сессионная кука покупателя** (httpOnly, отдельный ключ подписи) — не
  пересекается с админ-сессией; покупатель **не имеет доступа** к админке.
- **Личный кабинет** `/account`: профиль, **редактирование имени/телефона**
  (e-mail неизменяем в v1), **смена пароля**.
- **Инвалидция устаревших сессий**: при смене пароля счётчик `sessionVersion`
  увеличивается (поле `passwordChangedAt`), и **все ранее выданные токены на любых
  устройствах** становятся недействительными; текущему устройству выдаётся свежий токен.
- **История заказов** покупателя и **страница своего заказа** (жёстко ограничена по
  `customerId` — чужой заказ открыть нельзя).
- При оформлении залогиненным покупателем заказу проставляется `customerId`
  (на сервере, не с клиента). **Гостевое оформление полностью сохранено.**

**Безопасность авторизации и проверки готовности (Этапы 49A–53A)**
- **Аудит событий авторизации покупателя** (49A): регистрация/вход/выход, смена
  профиля/пароля и срабатывания лимита пишутся в журнал `AdminAuditLog`
  (`customer.*`) и видны в админке. Хранятся только тип события + id покупателя/
  `anonymous` + машинная причина — **никаких** паролей/кук/токенов/e-mail.
- **Устойчивый rate-limit авторизации** (49A → 51A): защита от перебора
  (login/register по IP; пароль/профиль по id покупателя) — теперь **DB-backed**
  (таблица `CustomerAuthThrottle`), счётчики **переживают перезапуск** (готовность к
  одно-инстансовому публичному демо; multi-instance — отдельный будущий этап).
- **Проверки готовности демо/продажи** (50A/52A/53A): `npm run demo:preflight`
  (security-гейт), `npm run demo:rehearsal` (репетиция), `npm run smoke:routes`
  (рендер + гейтинг админ-маршрутов), `npm run smoke:admin` (аутентифицированные
  админ-экраны локально), `npm run demo:sale-docs-check` (консистентность док-пакета).
  Всё локально, только чтение, без деплоя/секретов.

**Доверие и операции (Этап 59A)**
- **Отзывы с модерацией.** Покупатель (гость или залогиненный) оставляет отзыв с
  оценкой 1–5; отзыв уходит в статус «на модерации» и **публикуется только после
  одобрения** админом. На странице товара показываются **только одобренные** отзывы +
  средняя оценка и количество; если отзывов нет — честное пустое состояние. Это
  **модерируемый механизм**, без проверки факта покупки (демо-отзывы помечаются
  «Демо»). Текст валидируется на сервере (длина, без разметки/скриптов).
- **Модерация отзывов в админке** (`/admin/reviews`): одобрить / отклонить с записью
  в audit log; публично админ-раздел не виден.
- **Ручные детали доставки.** К заказу добавлены поля **отделение/склад** и
  **комментарий** (отдельно от старой свободной заметки). Это только ручной ввод
  клиента — **без** API перевозчика, живого справочника отделений, расчёта стоимости и
  накладных/трекинга. Видны в карточке заказа админки и в кабинете покупателя.
- **Основа e-mail операций (без реальной отправки).** Таблица `EmailOutbox` + шаблоны
  (подтверждение заказа / смена статуса / сброс пароля / подтверждение e-mail) с
  честным статусом записи. Провайдер **не** подключён, письма **не** отправляются —
  запись помечается «skipped» (зафиксировано, не отправлено), тело письма и токены
  **не** хранятся. Видно в `/admin/email-outbox`. Реальная отправка требует провайдера
  + домен/DNS (SPF/DKIM/DMARC) — отдельный этап под решение владельца.

**Основа восстановления доступа и подтверждения e-mail (Этап 60A) — без реальной отправки**
- **Провайдер-ориентированная архитектура писем.** Введён единый интерфейс провайдера
  (`EmailProvider`) с безопасной локальной реализацией **NoSend** по умолчанию: она
  **ничего не отправляет** и честно сообщает результат — `skipped_no_provider`
  (зафиксировано, провайдера нет) либо `failed_validation` (нет адреса). Заглушка
  `Stub` (`sent_stub`) существует только для будущей разводки и проверочного скрипта.
  Письмо в очереди (`EmailOutbox`) проходит обработчик «без отправки»: статус
  `queued → skipped_no_provider/failed_validation`, со счётчиком попыток и временем
  обработки. Запустить обработку очереди можно командой `npm run email:process:stub`
  (ничего наружу не уходит).
- **Основа сброса пароля.** Запрос сброса формирует **одноразовый короткоживущий токен**
  (TTL 45 минут), в БД хранится **только sha256-хэш** токена (таблица
  `CustomerAccountToken`) — открытый токен не пишется в БД, логи, админку или доки.
  Запрос всегда даёт **общий ответ** (не раскрывает, существует ли аккаунт), ограничен
  лимитом по IP и пишет событие в audit log. Подтверждение по валидному токену меняет
  пароль через тот же scrypt-механизм и **увеличивает `sessionVersion`** (все прежние
  сессии становятся недействительными); токен одноразовый. Страницы `/account/recover`
  (запрос) и `/account/reset` (подтверждение) уже есть. Так как провайдера нет, ссылка
  **не доставляется** реальному пользователю — основа провайдер-ориентирована, доставка
  под решение владельца.
- **Основа подтверждения e-mail.** Поле `Customer.emailVerifiedAt` + одноразовый
  хэшированный токен той же модели. В кабинете показывается статус (подтверждён / не
  подтверждён) и кнопка запроса письма-подтверждения; запрос фиксируется как намерение,
  но письмо **не** уходит (нет провайдера). Подтверждение e-mail **не требуется** для
  входа или гостевого оформления.
- **Видимость в админке.** На `/admin/email-outbox` добавлены счётчики попыток и
  безопасная сводка по токенам восстановления/подтверждения (**только числа**, без
  значений токенов). Токены, тела писем и секреты в админке не показываются.

**Каталог-UX, SEO и серверное «Избранное» (Этап 62A)**
- **Честный рейтинг на странице товара.** Звёзды/количество на карточке товара теперь
  берутся **из одобренных отзывов**: если отзывов нет — показывается честное
  «Ще немає відгуків», **без** фейковых 5 звёзд. Дизайн страницы не менялся.
- **SEO/мета.** Для страниц товара и категорий добавлены title, описание, базовый
  Open Graph и canonical. На странице товара — **структурированные данные** JSON-LD
  (`Product`: имя, описание, изображение при наличии, `offers` с ценой и валютой **UAH**,
  наличие). `aggregateRating` добавляется **только при наличии одобренных отзывов** —
  рейтинг/отзывы **не выдумываются**. Это только метаданные витрины — **не** заявка о
  реальном эквайринге/доставке.
- **Фильтры и сортировка каталога.** Сортировка по цене (↑/↓) и «спочатку новинки»
  (по реальной дате создания), фильтр наличия — через URL-параметры (можно делиться
  ссылкой). Невалидные параметры **безопасно** откатываются к значению по умолчанию;
  скрытые/недоступные товары не показываются как покупаемые.
- **Серверное «Избранное» для аккаунта.** Для **залогиненного** покупателя избранное
  **сохраняется в БД** (`CustomerWishlistItem`) и переживает смену устройства/сессии;
  раздел «Обране» виден в кабинете. **Гостевое** избранное (localStorage) сохранено
  без изменений. Список **жёстко привязан к `customerId`** (одно избранное не видно
  другому), показываются **только опубликованные** товары; удаление товара/аккаунта
  чистит записи каскадом. Добавление идемпотентно.

**Промокоды / скидки на оформлении (Этап 63A) — ручной чекаут, без платёжных провайдеров**
- **Промокоды в админке** (`/admin/promotions`): создание/редактирование, **процент** (1–100)
  или **фиксированная сумма** (₴), мин. сумма заказа, кап на макс. скидку, окно действия
  (старт/финиш), лимит использований, заметки. Включение/выключение и **архивирование**
  (мягкое удаление — без жёсткого `delete`, чтобы история заказов оставалась читаемой).
  Все поля валидируются на сервере; действия пишутся в audit log.
- **Применение на чекауте.** Покупатель вводит **только строку кода**; сервер заново считает
  цены/подытог из БД и **сам вычисляет скидку** — клиентскую скидку/итог никогда не
  доверяем. Деньги — целые **минор-единицы (₴)**: процент округляется в минор-единицах и
  **кэпится** `maxDiscount`, фиксированная скидка **не превышает** подытог, **итог никогда не
  отрицательный**. Невалидный код **не блокирует** заказ — показывается общая ошибка.
- **Снимок в заказе.** На заказе сохраняются `discountMinor` + код (`promoCode`); скидка видна
  в админ-карточке заказа, в кабинете покупателя и в подтверждении. Старые заказы не меняются
  (скидка 0, итог прежний).
- **Лимит использований — потокобезопасно.** `usedCount` увеличивается **транзакционно**
  только при успешном создании заказа (guard `usedCount < usageLimit`); при достижении лимита
  заказ с этим кодом не проходит. Отмена заказа `usedCount` **не уменьшает** (сознательно —
  без сложного реестра погашений; задокументировано).

**Продвинутый поиск и фильтры каталога (Этап 64A) — локально, без внешних сервисов**
- **Диапазон цены.** URL-параметры `minPrice`/`maxPrice` (₴). Валидация на стороне сервера-логики:
  отрицательные/нечисловые/огромные значения **безопасно игнорируются**, `min > max`
  **меняются местами**. Деньги — целые единицы. Ссылку с фильтром можно расшарить.
- **Фильтр по матеріалу/покриттю.** Значення фасета **виводяться з реальних даних** товарів
  (покриття варіантів: Позолота / Родіювання / Сталь) — **нічого не вигадується**; фільтр
  показується, лише коли є дані. Невідоме значення → відкат до «будь-який матеріал».
- **Багатший пошук.** Локальний (БД-снапшот) пошук за назвою, описом, артикулом, категорією,
  тегами, характеристиками **та матеріалом/покриттям**; запит нормалізується (trim, ліміт
  довжини, відкидання розмітки), дивний Unicode не ламає пошук. **Без зовнішніх пошукових
  сервісів і без AI.**
- **Сортування за рейтингом — чесне.** Нові варіанти «За рейтингом» / «За кількістю відгуків»
  рахуються **лише за схваленими відгуками** (pending/rejected не враховуються; товари без
  відгуків — у кінці, рейтинг не вигадується). Детерміновані tie-break (рейтинг → кількість →
  новизна → назва). Старі сортування збережені.
- **Порожні стани й активні фільтри.** Чесний порожній стан + зведення активних фільтрів
  (наявність / ціна / матеріал / сортування) з кнопкою «Скинути все». Дизайн карток/галереї
  не змінювався.

**Дашборд операций в админке (Этап 65A) — командный центр владельца (локально)**
- **`/admin/dashboard`** переработан в обзор по **реальным данным** БД: заказы (по статусам +
  последние), отзывы (на модерации/одобрено/отклонено), промокоды (активные/выключены/архив/
  исчерпан лимит/скоро истекут), почта-outbox (в очереди/не отправлено-нет-провайдера/ошибки),
  состояние каталога (опубликовано/скрыто/без цены/без изображения/нулевой остаток),
  покупатели (агрегаты: всего/подтверждён e-mail/новые за 7 дней/избранное).
- **«Требует внимания»** — единая очередь задач с приоритетом (Действие / Внимание / Инфо) и
  ссылкой на нужный раздел: новые заказы, отзывы на модерации, письма в очереди/с ошибкой,
  товары без цены/изображения, нулевой остаток у доступных, промокоды (лимит/срок) и т. д.
- **Честные предупреждения готовности** (под решение владельца): реальная отправка e-mail НЕ
  настроена, онлайн-оплата/перевозчик НЕ подключены, публичного деплоя нет, админка локальная,
  часть фото — плейсхолдеры, внешней BI/аналитики нет. Это инфо/предупреждения, не «ошибки».
- **Только безопасные агрегаты.** Не показываются секреты, токены, cookie, тела писем, сырые
  payload’ы и персональные данные покупателей. Команды проверок (`demo:preflight` и т. п.)
  отображаются **как текст-документация** — из веб-админки ничего не выполняется.

**Покупатели и поддержка в админке (Этап 68A) — только просмотр, локально**
- **`/admin/customers`** — список аккаунтов с поиском (e-mail/имя) и фильтрами (подтверждён e-mail /
  есть заказы / есть избранное). Показаны только безопасные поля: короткий ID, e-mail, имя, телефон,
  статус подтверждения e-mail, дата регистрации, счётчики заказов/отзывов/избранного и дата
  последнего заказа.
- **`/admin/customers/[id]`** — карточка покупателя: профиль, счётчики, последние заказы (со ссылкой
  на карточку заказа), отзывы (со ссылкой на модерацию), избранное (с пометкой «недоступен»), события
  писем (только безопасные метаданные) и **сводка поддержки** с честными сигналами (не подтверждён
  e-mail, нет заказов, отзывы на модерации, проблемные письма, недоступные товары в избранном,
  активный запрос восстановления, ручная доставка без телефона).
- **Это не CRM и не support-desk.** Раздел **только читает** — нельзя редактировать, удалять или
  «входить как покупатель». Не показываются: хэш пароля, значения/хэши токенов, cookie/сессии, тела
  писем, адреса получателей и сырые payload’ы. Токены восстановления/подтверждения — **только числа**
  (всего / активные), без значений. Админка остаётся локальной (в проде маршруты отдают 404).

## 2. 🟡 Ручной MVP (работает, но без интеграций — это сознательная модель)

- **Оплата — ручная.** `paymentMethod` хранит выбор клиента
  (`cash_on_delivery` / `manual_online`). **Нет** реального эквайринга, списания,
  вебхуков и состояния «оплачено». Деньги подтверждаются вне системы.
- **Доставка — ручная.** `deliveryMethod` + ручные поля **отделение/склад**, **адрес**
  и **комментарий** (`deliveryBranch` / `deliveryDetails` / `deliveryComment`).
  **Нет** API перевозчика, живого справочника отделений, расчёта стоимости, модели
  адреса, трекинга и печати накладных — поля заполняет сам клиент.
- **Обработка заказа — ручная.** Статусы двигает админ вручную; нет
  авто-уведомлений и авто-фулфилмента.
- **Тексты оплаты/доставки на чекауте — редактируются в админке** (Этап 46F):
  названия и пояснения способов, заметки оформления и подтверждения правятся в
  `/admin/settings`. Это только **текст** — ключи способов и серверная логика
  заказа не меняются, реального эквайринга/API перевозчика по-прежнему нет.
- **Демо-данные — посевной каталог** (10 товаров), не финальная витрина бренда
  покупателя.
- **Изображения товаров — плейсхолдеры** (нет реальных фото): слоты под фото/галерею
  есть, но реальных снимков нет. Это главный оставшийся визуальный пробел демо —
  план закрытия в [`PRODUCT_IMAGERY_GAP_PLAN.md`](./PRODUCT_IMAGERY_GAP_PLAN.md).

## 3. 🔧 Будущее / зависит от провайдера или решения владельца

Каждый пункт — **отдельный, отдельно оплачиваемый** этап; многие требуют решений
владельца и **актуальной официальной проверки** (юрлицо, провайдер, тарифы):

- **Платёжный провайдер** (LiqPay / Fondy / WayForPay / банковский эквайринг):
  модель `Payment`, подписанные вебхуки, идемпотентность, возвраты. *(Спеки-основания
  существуют: см. `docs/PAYMENTS_SPEC.md`, `docs/PAYMENT_PROVIDER_DECISION.md`.)*
- **Интеграция доставки** (Новая Почта / Укрпочта API): модель адреса, расчёт
  стоимости, трекинг, печать накладных. Ручные поля отделения/комментария **уже есть**
  (§1/59A) и станут естественным местом для выбранного отделения после интеграции.
  *(См. `docs/DELIVERY_SPEC.md`.)*
- **Уведомления** (email / SMS): **основа e-mail заложена** (`EmailOutbox` + шаблоны +
  обработчик «без отправки», §1/59A/60A), но **реальная отправка не подключена** — нужен
  провайдер. Подтверждение заказа, смена статуса, сброс пароля и подтверждение e-mail
  доставляются только после подключения провайдера и настройки домена (SPF/DKIM/DMARC).
- **Доработки личного кабинета**: базовые аккаунты, вход, профиль, смена пароля,
  история заказов, **аудит событий авторизации**, **устойчивый rate-limit**, а также
  **основа сброса пароля и подтверждения e-mail на одноразовых хэшированных токенах**
  (§1, этапы 47A–47C/49A/51A/60A) **уже есть**; остаются на будущее — **реальная
  доставка** писем сброса/подтверждения (нужен провайдер), книга адресов, **слияние
  гостевых заказов** с аккаунтом по e-mail, **multi-instance** rate-limit и **журнал
  устройств/сессий**.
- **Отзывы и рейтинги — базовый модерируемый механизм уже есть** (см. §1/59A): на
  будущее остаются проверка факта покупки, фото в отзывах и ответы магазина.
- **Серверные фильтры / фасеты / пагинация** для большого каталога.
- **Мультиязычность (uk-UA / EN)** и вторичные валюты **EUR / USD** как
  экспортно-готовое будущее (не путь оплаты v1).
- **Продакшн-деплой** (домен, хостинг) — за отдельным чек-листом готовности и
  явным согласием владельца.
- **Фискализация (РРО / ПРРО)**, чеки, юридическое соответствие — **вопрос к
  юристу/провайдеру**, требует актуальной официальной проверки.

## 4. 🚫 Чего пока нет (не входит в текущий продукт)

- Нет реального приёма онлайн-платежей.
- Нет интеграции с перевозчиками и трекинга (ручные поля отделения/комментария есть — §1/59A).
- Нет реальной отправки email/SMS — письма **не** уходят; есть только основа `EmailOutbox`
  + обработчик «без отправки» (§1/59A/60A), который фиксирует запись как
  «skipped_no_provider».
- Нет **доставки** писем сброса пароля и подтверждения e-mail — нужен провайдер. Основа
  на **одноразовых хэшированных токенах** (`CustomerAccountToken`), страницы
  `/account/recover` и `/account/reset`, статус `emailVerifiedAt` и инвалидция сессий
  при сбросе **уже есть** (§1/60A), но ссылка реальному пользователю **не доставляется**.
- Нет проверенных отзывов о покупке и фото в отзывах (модерируемые отзывы уже есть — §1/59A).
- **Ручные промокоды/скидки уже есть** (§1/63A). Но НЕТ: **подарочных сертификатов**;
  **стэкаемых** промокодов (один код на заказ, не суммируются); **автоматических/маркетинговых
  кампаний** и **email-маркетинга/CRM**; скидок **на стороне платёжного провайдера**. Это
  отдельные будущие этапы.
- **Поиск/фильтры каталога уже есть локально** (§1/64A: цена, материал, богатый поиск,
  сортировка по рейтингу). Но НЕТ: **AI/семантического поиска**, **внешнего поискового
  движка** (Algolia / Elasticsearch / …) и **автоматизации мерчандайзинга/рекомендаций**.
- **Дашборд операций уже есть** (§1/65A). Но НЕТ: **внешней BI/аналитики**; из веб-админки
  **нельзя** запускать shell/CLI-команды (имена команд — только текст-документация).
- **Просмотр покупателей и сводка поддержки в админке уже есть** (§1/68A, только чтение). Но НЕТ:
  **полноценной CRM-платформы**; **внешнего support-desk/helpdesk** (Zendesk/Intercom/…);
  **«входа как покупатель»** (impersonation); публичной клиентской админки; видимости/управления
  **значениями токенов**.
- Нет фискализации/чеков и юридических гарантий соответствия.
- Нет развёрнутого продакшн-магазина «из коробки».
- Нет мультиязычности uk-UA/EN из коробки.
- Нет автоматического **браузерного** E2E-теста сквозного сценария (опциональный
  будущий этап). Есть, однако, **HTTP-смоук рендера** (`smoke:routes`, 23 маршрута) и
  **аутентифицированный админ-смоук** (`smoke:admin`), а серверная логика покрыта
  проверочными скриптами `db:verify:*` (откатываемые транзакции).

## 5. Краткое резюме для покупателя

AURELIA закрывает **самое дорогое в разработке**: витрину на БД, админку, варианты
товаров, остатки, сквозной поток заказа с серверно-авторитетной ценой и
контролируемым жизненным циклом, **а также аккаунты покупателей** (вход, профиль,
смена пароля с инвалидцией сессий, история заказов; гость сохранён), **отзывы с
модерацией**, **ручные детали доставки** (отделение/комментарий), **основу e-mail
операций**, а также **SEO/мета + структурированные данные**, **фильтры/сортировку
каталога** и **серверное «Избранное»** для аккаунта (§1/62A), **ручные промокоды/скидки**
с серверно-авторитетным расчётом (§1/63A), и **продвинутый локальный поиск/фильтры каталога**
(цена, материал, богатый поиск, честная сортировка по рейтингу — §1/64A), **дашборд операций
в админке** с очередью «Требует внимания» (§1/65A), и **просмотр покупателей со сводкой поддержки**
в админке (только чтение — §1/68A). **Оплата и доставка пока
ручные** (честная стартовая модель для Украины),
**письма пока не отправляются** (есть только основа), а провайдерные интеграции,
реальная отправка уведомлений, e-mail-функции аккаунта (сброс/подтверждение),
локализация и продакшн-деплой — это **следующие, отдельно оплачиваемые** этапы, а не
скрытые «недоделки».
